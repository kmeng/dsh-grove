# 评审清单

评审时逐条过，不凭感觉。可以只针对改动的一类，但不能跳过。

## 代码改动

- [ ] 与 issue 里确认过的方案一致，没有夹带无关改动
- [ ] 失败路径与边界情况有测试（空输入、缺文件、错误版本）
- [ ] 新增的断言**真的会失败**：把实现改坏一次，确认测试变红
- [ ] 没有把"应该通过"写成"已通过"
- [ ] 报错信息能让人知道下一步做什么

## bundle 契约

- [ ] `engines.dsh` 仍是范围，不是精确版本
- [ ] 宿主包同时声明在 `peerDependencies` 与 `devDependencies`，且是范围
- [ ] `exports` / `files` 与仓库实际文件一致
- [ ] `cordis.patch.yml` 插入的 `name` 与包名一致

## 文档与素材

- [ ] 双语版本口径一致，不是摘要对全文
- [ ] 图片尺寸、透明通道、对比度符合 `brand/VI.md`
- [ ] 生成的 PNG 与源文件同步（重跑过 `build.sh`）

## 发布前

- [ ] `npm test` 全绿
- [ ] `scripts/check-compat.sh` 判定 compatible
- [ ] `npm pack --dry-run` 清单正确
- [ ] 临时 profile 安装验证过并清理

## 评审提示

- 你说"看起来没问题"的时候，问一句：**哪条命令证明了它？**
- 用户反馈的问题必须用户确认才能关闭；自己发现的缺陷可以自己关。
- 影响面大的决定（接口、依赖、发布方式）等拍板，不要替用户决定。
